Staff feedback — August 2026

Thirteen items raised by FSM staff after running the app at the counter. This page is the running record of what each item meant in the code and how it was resolved, so the fixes stay traceable back to the request that prompted them.

Items are delivered in three batches: the small, self-contained fixes first, then the ones needing new schema, then the New Transaction / Capture Visit merge.

Batch 1 — delivered

1 · Loyalty lookup clears itself

The counter device is shared, so a number left in the lookup field is both a privacy leak and a mis-scan waiting to happen.

  • Android — LoyaltyLookupCard (Home) and LoyaltyLookupScreen (public) held the typed number in rememberSaveable while the view model held the result, so both survived navigating away. A LifecycleResumeEffect now clears the field and resets the view model as soon as the screen stops being the foreground destination.
  • Web — the lookup input is marked data-clear-on-restore and cleared on turbo:before-cache (so the snapshot Turbo restores from is empty) and on a bfcache pageshow. A value the server deliberately re-rendered — the number that failed validation — is left alone. autocomplete is off.

3 · Three customer types, named consistently

The three types already existed (drive_in / otp / credit); the wording and order did not. Customer::CUSTOMER_TYPE_LABELS is now the single source — Drive-In, Credit, Fleet/OTP, in that order — and every picker, filter chip and badge reads from it (Customer.customer_type_options / customer_type_label_for) instead of hardcoding a list or calling humanize. The Android filter chips mirror the same list.

4 · Two payment types

Already correct on every surface: Transaction#payment_mode is { cash, credit }, and the web radio group and the Android payment options offer exactly those two. No change.

5 · Settlement defaults to yesterday

Staff record the day's transactions as they happen and settle the next morning, so a draft opened with no date now loads yesterday's sheet (Settlement::Builder.default_business_date). An unparseable date falls back to the same default. The pump/date chooser still lets the FSM pick any date, and Android picks the default up from the draft API.

7 · ₹2 and ₹1 in the cash counter

SettlementCashDenomination::DENOMINATIONS is now 500, 200, 100, 50, 20, 10, 5, 2, 1. The form grid, the draft API and the Android denomination rows all derive from that constant, so one change covers all three. Existing settlements gain the two new rows when reopened.

8 · Discount on New Transaction

Transaction#discount_amount existed and was permitted, but no form ever set it. Added on the web fuel step and the Android transaction screen, with the submit gate refusing a negative discount or one that swallows the sale.

TransactionCreator previously applied a discount only on the litres path; the web form captures ₹, so the typed-amount path now treats the figure as the gross and takes the discount off it. Points are earned on the net — what the customer actually paid.

9 · Credit line type is the customer type

SettlementCreditLine#credit_type was fleet_otp / tank_truck. It now mirrors the three customer account types. fleet_otp keeps its stored value (0) so installed app builds keep posting a value the server accepts; tank_truck (1) was migrated to credit (3), which is what a tank-truck credit sale was being used to record. The Android type toggle became a three-way segmented control.

Batch 2 — delivered

6 · Settlements no longer multiply, and staff can read the day's sheet

Two separate problems behind one line of feedback.

The multiplying. The Android form kept null ids on its child rows after the first save — the response was only read for the settlement's own id. A second submit therefore posted every reading, lube, credit and denomination as a new nested record, so the sheet ended up with two of everything and double the totals. Three changes:

  • The app now re-reads the saved settlement into the form after each save, so every row carries the id it was handed back.
  • DailySettlement refuses a payload containing two rows for the same nozzle, lube, denomination, digital means, stock line or rate comparison, with a message the FSM can act on.
  • Matching unique indexes make the duplicate impossible even under a race, and the migration deduplicates rows already written (newest wins) and re-derives every affected settlement's stored totals.

Credit and discount lines are deliberately not deduplicated: they have no natural key, so a second row there may be a genuine second credit.

The report. accessible_settlements scoped staff to recorded_by: current_user, so an FSM couldn't see the sheet for their own pump if a colleague on another shift had recorded it. Staff now read any settlement for a pump they're posted to (their standing assignment or any dated one) while still editing only their own; the list shows who recorded each row and hides Edit on the rest.

10 · Digital receipts are free-form

phonepe_pos_amount and phonepe_scanner_amount were two fixed columns. They are now settlement_digital_receipts — a repeatable label + amount line, so PAYTM or any other means can be recorded without a release. PhonePe POS and PhonePe Scanner are seeded on every draft, so the sheet still looks the way the FSM expects. Existing values were migrated into rows and the columns dropped.

For compatibility, the staff API still accepts the two old parameters (folding them into the matching labelled rows) and still emits both keys, derived from those rows — an app build already on a phone keeps working.

11 · A discount can be added during settlement

Discount lines used to arrive only pulled from the same day's visit entries. The settlement form now has an Add discount row on both surfaces for one missed at capture; a line with no visit entry is a manually added one. Empty rows are dropped rather than saved.

12 · Cash taken out

New settlement_expense_lines (description + amount) for a salary advance or anything else taken from the day's takings. It reduces the Final Amount to Settle, so the counted cash still reconciles:

final = (fuel + lubes) − (discounts + credit + digital receipts + cash taken out)

13 · Notes are a dated log

customers.info_note was one text column that every save overwrote, so the previous conversation was lost. Notes are now customer_notes — append-only, each with its author and timestamp. The existing note was carried over as the first entry (stamped with the customer's last update, the closest available approximation) and the column dropped.

Assigning info_note still works on all three surfaces — it queues a new dated entry instead of overwriting the last — and reading it returns the most recent entry, so older app builds and existing API consumers are unaffected. The note box on the web form and in the app now starts empty, with the full log rendered beneath it.
