Nayara Admin — native app, three directions

Same data, same tokens, three different bets about what an admin opens the app to do. Every screen is tappable: switch tabs, open a customer, record attendance, run the command palette. Tokens are pulled verbatim from docs/design/tokens.css.

Option A · Console

Faithful port. Data first.

The web console, made thumb-native. Home is the analytics overview: hero card, swipeable KPI rail, charts. Four tabs mirror the sidebar groups so muscle memory transfers 1:1. Lowest risk, ships fastest — but it inherits the web console's core flaw: it answers "how are we doing?" and never "what needs me?"

4 tabsDashboard-firstZero re-trainingReads, not acts
Option B · Signal

Triage first. Numbers on demand.

Home is a "needs you today" feed — attendance unrecorded, schedule failed, pump nozzle down, staff unassigned — each card carrying its own one-tap fix. Analytics moves to its own tab. Center FAB matches the staff app, so both apps feel like one product. Best fit for how an owner actually uses a phone: 40 seconds, standing up, deciding something.

4 tabs + FABAlert-drivenActs, then reportsNeeds alert rules
Option C · Palette

Search is the navigation.

No tab bar. A single scrollable home of reorderable widgets, and one persistent command bar: type "att", get Record Attendance; type a plate, get the customer. All 15 admin sections become searchable, not navigable — the IA stops fighting the 5-tab ceiling. Scales as you add sections; costs the most to build and teach.
